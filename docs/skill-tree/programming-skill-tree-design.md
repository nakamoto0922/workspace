# プログラミング学習用スキルツリーアプリ 設計メモ

## 1. 設計方針

本アプリは「現在の実力を記録する仕組み」ではなく、**習得したい内容を構造化し、小目標として管理する仕組み**として設計する。

そのため、ノードはスキル値や経験値ではなく、**学習のための目標単位**として扱う。

また、プログラミング学習では後から学習構造を見直すことが多いため、最初から固定されたツリーとして作るのではなく、**あとから柔軟に編集・再構成できること**を重視する。

---

## 2. 設計上の基本思想

### 2.1 ノードは「小目標」
ノードは「Reactを理解する」のような抽象的な概念ではなく、できるだけ達成判定可能な目標にする。

例:
- props を使ったコンポーネントを作る
- useState で状態を持つ
- fetch で API の結果を表示する

### 2.2 学習構造は固定しない
学習中には以下のような変更が自然に発生する。

- 前提知識が足りなかったので途中にノードを追加したい
- ノードが大きすぎたので分割したい
- 細かすぎるので統合したい
- 所属カテゴリを変えたい
- 前提条件を増やしたい

そのため、初期設計では「正しい完成ツリー」を目指さず、**編集されることを前提とした構造**にする。

### 2.3 見た目はツリー、内部はグラフ寄り
画面上はツリー表示を採用するが、内部データは純粋な木構造に限定しない。  
理由は、ノード間の依存関係が単純な親子関係では表現しきれないためである。

例:
- `ReactでAPI通信する` は React 配下に見せたい
- しかし前提として JavaScript の非同期処理理解も必要

このようなケースに対応するため、**分類上の親子関係**と**前提条件としての依存関係**を分離して持つ。

---

## 3. ノード設計

## 3.1 ノードの役割
ノードは以下の3階層を想定する。

### Goal
大きな到達目標

例:
- TypeScript基礎を身につける
- React基礎を身につける

### Topic
まとまりのある学習単元

例:
- props
- state
- hooks
- 型推論

### Task
実際にチェックする小目標

例:
- props を使って親から子へ値を渡す
- useState でカウンターを作る
- interface でオブジェクト型を定義する

初期実装では、少なくとも Topic / Task の区別を持たせると扱いやすい。

---

## 3.2 ノードに持たせたい属性

### 必須
- id
- title
- description
- type
  - goal
  - topic
  - task
- status
  - locked
  - available
  - completed
- parentId
- prerequisiteNodeIds
- order

### 任意
- tags
- referenceLinks
- memo
- difficulty
- createdAt
- updatedAt

---

## 4. 関係性の設計

### 4.1 parentId
見た目上の所属先を表す。

例:
- `useState で状態を持つ`
  - parentId = React / state

### 4.2 prerequisiteNodeIds
解放条件として必要な前提ノードを表す。

例:
- `ReactでAPIの結果を表示する`
  - prerequisiteNodeIds
    - JavaScriptで非同期処理を理解する
    - useStateで状態を持つ

この2つを分けることで、分類と依存を独立して扱える。

---

## 5. ステータス設計

ノードの状態はシンプルに始める。

- locked: まだ着手不可
- available: 着手可能
- completed: 完了

初期段階ではこれで十分。  
将来的には以下の追加も考えられる。

- in_progress
- archived
- hidden

ただし v1 では状態を増やしすぎない方がよい。

---

## 6. 完了条件の考え方

初期実装では、ノードの完了は基本的に**手動チェック**とする。  
理由は以下の通り。

- 自動判定は実装コストが高い
- ノードごとに達成条件が異なる
- 学習の柔軟性を妨げたくない

将来的には、以下のような補助条件を追加できる。

- 特定の前提ノード完了
- 子ノードの一定数完了
- メモ入力
- 参考リンク消化フラグ

ただし v1 では、複雑なルール化は避ける。

---

## 7. ノード粒度に関する方針

### 7.1 大きすぎるノードを避ける
以下のようなノードは大きすぎる。

- Reactを理解する
- TypeScriptを使えるようになる
- 設計力を身につける

理由:
- 終了条件が曖昧
- 達成感が弱い
- 後から分割したくなる

### 7.2 小さすぎるノードも避ける
以下のようなノードは細かすぎる可能性がある。

- importを書く
- exportを書く
- セミコロンをつける

理由:
- 単独の学習単位として弱い
- ツリーがノイズ化しやすい

### 7.3 粒度の目安
**1つの意味ある学習単位であり、達成のイメージが持てること**  
を目安にする。

例:
- props を使うコンポーネントを作る
- useEffect で副作用を扱う
- WHERE 句を使って絞り込み検索を書く

---

## 8. 柔軟性のために必要な編集操作

本アプリでは、以下の編集操作を重要機能とみなす。

### 8.1 分割
1つの大きなノードを複数のノードに分ける。

例:
- hooks を理解する
  ↓
- useState を使う
- useEffect を使う
- custom hooks を知る

### 8.2 統合
細かすぎるノードをまとめる。

### 8.3 挿入
ノードの途中に新しい前提ノードを入れる。

例:
- 非同期処理
  → ReactでAPI通信
の間に
- Promise を理解する
を追加

### 8.4 移動
所属カテゴリを変更する。

### 8.5 依存関係変更
前提ノードの追加 / 削除 / 差し替えを行う。

これらの操作をしやすくすることが、アプリ全体の寿命を延ばす。

---

## 9. 画面設計の基本方針

## 9.1 ツリー画面
役割:
- 学習全体の構造を見る
- ロック / 解放 / 完了状態を把握する
- どのノードがどこにつながっているか確認する

要件:
- ノード状態の視認性
- 折りたたみ
- クリックで詳細表示
- 編集導線

## 9.2 ノード詳細画面
役割:
- ノードの内容確認
- 完了操作
- 参考情報確認
- 編集

表示内容:
- タイトル
- 説明
- 前提ノード
- 子ノード
- メモ
- リンク
- 完了ボタン
- 編集ボタン

## 9.3 今やること画面
役割:
- `available` なノードだけを一覧表示する
- 実行用の ToDo リストとして使う

この画面があることで、全体マップと日々の行動をつなげやすくなる。

---

## 10. 最小実装に必要な範囲

v1 では以下に絞る。

- ノード作成
- ノード編集
- ノード削除
- parentId による所属管理
- prerequisiteNodeIds による前提管理
- status 管理
- ツリー表示
- ノード詳細表示
- 手動完了
- 着手可能ノードの抽出

この範囲であれば、コンセプトを保ちながら現実的に実装しやすい。

---

## 11. 後回しにしてよい要素

以下は重要そうに見えるが、初期段階では優先度を下げる。

- 経験値システム
- 成長の自動解析
- 学習行動ログからの自動反映
- GitHub / ChatGPT など外部連携
- 高度な進捗分析
- 過剰なゲーム演出

本アプリのコアは、まず**小目標を構造化し、順番に潰していける状態を作ること**にある。

---

## 12. 技術的に意識したいこと

- データ構造は木構造に閉じない
- ノードIDを安定して持つ
- 順番変更や移動に耐えられること
- 前提関係の循環を防ぐこと
- 状態計算をシンプルに保つこと

特に依存関係を持つ以上、循環参照のチェックは必要になる。

---

## 13. 今後の拡張方向

- ノードテンプレート
- 学習テーマごとの複製
- 進捗率の自動計算
- 振り返りメモ
- 分割候補 / 統合候補の提案
- AI によるノード分解支援

ただし、これらは v1 の成功後に検討すればよい。

---

## 14. まとめ

設計の中心は以下の通り。

- ノードはスキル値ではなく「小目標」
- 見た目はツリー、内部はグラフ寄り
- 親子関係と前提条件を分ける
- 最初から完璧なツリーを目指さない
- あとから分割・追加・移動しやすい構造にする
- v1 はシンプルな状態管理と手動完了に絞る

この方針により、学習を進めながらツリー自体も育てていける、柔軟な学習アプリの基盤を作れる。
